# Ten-step loop — 결과를 먼저 정의하고, 10단계로 나눠, 단계마다 눈으로 확인하며 완성한다

이 사용자는 "결과를 먼저 정의하고 캡처·계측으로 단계마다 확인하는 반복"을 원한다. 묻지 말고 스스로 목표를 세우고 끝까지 간다.
핵심은 **추측으로 넘어가지 않는 것**이다: 매 단계가 끝나면 실제 렌더를 캡처해 보고(또는 수치를 재고) 목표표와 비교한 뒤, 미달이면 같은 단계 안에서 고친다.

## 0. 시작 전에 읽을 것
- 프로젝트 문맥: `README.md`, `scripts/visual-check/*.md` 중 가장 최근 결과 문서(예: `MANTA.md`, `RESORT.md`). 이전 루프가 남긴 "단계별 기록"의 함정이 그대로 재발한다.
- 품질 기준선: 기존 결과물의 캡처(`.visual-check/step*/matrix/sheet.png` 등)를 Read 로 직접 본다. "상어 수준" 같은 요구는 이 그림이 기준이다.
- Aqua 에 **생물을 추가**하는 작업이면 `references/creature-pipeline.md` 를 먼저 읽는다 (파일 목록·순서·함정).
- 캡처·계측 명령은 `references/capture-tools.md`.

## 1. 목표 정의 문서를 먼저 쓴다 — `scripts/visual-check/<이름>.md`
형식은 기존 문서(MANTA.md)와 같게:
1. 기준선(before) 한 줄, 요청 한 줄, 품질 기준이 되는 캡처 경로.
2. **목표표** `| # | 항목 | 목표 |` — 항목 10개(G1..G10). 각 목표는 캡처나 수치로 **판정 가능**해야 한다("예쁘게" ✗, "위에서 보면 등딱지 육각 무늬가 보인다" ✓, "draws ≤ 64" ✓).
   - 마지막 두 개는 항상 **성능**(fps·draws·tris·GPU ms·콘솔 에러 0, 기존 수치 대비 예산)과 **코드**(tsc/lint 0, 문서 갱신, 기존 결과물 변화 없음)로 둔다.
3. **단계표** 1..10 — 각 단계가 어느 목표(G#)를 닫는지 적는다. 보통: 파이프라인/뼈대 → 형태(실루엣) → 형태 다듬기 → 재질 → 디테일/부품 → 움직임 → 화면 A 통합 → 화면 B 통합 → 성능 → 정리·문서.

목표표 없이 구현부터 시작하지 않는다. 나중에 "됐다"고 말할 근거가 이 표다.

## 2. 단계 루프 (1..10 순서대로, 건너뛰지 않는다)
각 단계에서:
1. **구현** — 그 단계 목표에 필요한 최소 변경. 관련 없는 리팩터링은 섞지 않는다.
2. **검증 통과** — `npx tsc --noEmit -p .` 와 `npx eslint src scripts` 가 0 이어야 캡처로 넘어간다.
3. **캡처/계측** — `.visual-check/step<접두사><n>/` 에 저장. 형태 단계는 여러 방향(`?view=top|side|front|below`)을 한 시트로 합쳐 본다. 움직임은 시간차 프레임 2~4장. 통합 단계는 전체 화면. 성능 단계는 `check:render`.
   - 캡처는 **반드시 Read 로 직접 본다**. 파일이 생겼다고 끝이 아니다.
   - "안 보인다/똑같다" 판단은 눈이 아니라 PIL 픽셀 diff 로 확인한다(실제로는 움직이고 있던 경우가 있었다).
4. **비교** — 목표표의 해당 G# 와 대조해 ✓/△/✗ 를 속으로 매긴다. 기준 캡처(상어 등)와 나란히 놓고 본다.
5. **미달이면 같은 단계에서 수정** — 원인을 적고 고친 뒤 다시 캡처. 보통 2~3회 안에 닫힌다. 3회를 넘기면 목표가 잘못됐는지 의심하고 목표를 **문서에 적고** 조정한다(몰래 낮추지 않는다).
6. **기록** — 문서의 "단계별 기록"에 그 단계에서 무엇이 틀렸고 어떻게 고쳤는지 한두 줄. 다음 루프(다른 생물)가 같은 함정을 피하게 하는 가장 값진 산출물이다.

사용자에게는 단계 전환마다 한두 문장으로 "무엇을 봤고 무엇이 미달이라 무엇을 고친다"를 알린다. 질문으로 멈추지 않는다 — 판단이 갈리면 기본값을 고르고 문서에 적는다.

## 3. 마지막 단계(정리)에서 반드시
- 목표표 아래에 **결과표** `| # | 항목 | 결과 | 판정 |` 를 채운다. 수치는 실제 계측값(기기·해상도 명기). 미판정은 △ 와 이유.
- 기존 결과물이 변하지 않았음을 **캡처로** 증명한다(예: 상어 매트릭스 재촬영). 베이크 스크립트를 건드렸으면 기존 생물도 다시 구워 본다.
- README 의 구조·명령 설명, 메모리(프로젝트 문맥) 갱신.
- 최종 보고: 결과표 요약 + 캡처 경로 + 미달/보류 항목을 숨기지 않고 쓴다.

## 4. 이 저장소에서의 절대 규칙
- 개발 서버(3000)는 사용자가 띄워 둔 것 — `pkill -f next-server` 류 광범위 kill 금지. 포트나 PID 로만 죽인다.
- 캡처 스크립트가 가끔 브라우저 종료에서 멈춰 `wait` 가 안 끝난다 → `ps -eo pid,etime,command | grep shot.mjs` 로 해당 PID 만 kill.
- 같은 저장소에서 다른 세션이 동시에 작업할 수 있다(파일이 "changed on disk" 로 뜨면 그 변경을 존중하고 덮어쓰지 않는다).
- 커밋은 사용자가 요청할 때만.
- 품질과 정확성은 타협하지 않는다. 목표를 못 닫았으면 못 닫았다고 쓴다.
